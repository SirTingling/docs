Every API request requires an API key in the `Authorization` header.

## Authenticating requests

Pass your API key as a Bearer token:

```bash
curl https://cloud.takumo.io/api/v1/rules \
  -H "Authorization: Bearer your-takumo-api-key"
```

In code:

```typescript
const response = await fetch("https://cloud.takumo.io/api/v1/rules", {
  headers: {
    "Authorization": `Bearer ${process.env.TAKUMO_API_KEY}`
  }
});
```

The gateway (`gateway.takumo.io/v1/messages` and `/v1/chat/completions`) takes the same `Authorization: Bearer` header. See [AI Tools](/ai-tools/overview).

<Warning>Authenticating a self-hosted gateway with Takumo API keys is not yet available. Contact Takumo support at [support@takumo.io](mailto:support@takumo.io) to set up on-prem access.</Warning>

## How keys are validated

1. Takumo receives your key from the `Authorization` header.
2. It computes a SHA-256 hash of the raw key.
3. The hash is looked up in the database.
4. A deleted, disabled or expired key is refused with `401`. A key stops working at the moment it expires.
5. A key without the scope the route needs is refused with `403`, and the response names the scope. The gateway checks one scope, `gateway:proxy`, and its `403` does not name it.
6. If your organization has an IP allowlist, a request from outside it is refused with `403`.
7. Otherwise the request proceeds.

Every request is checked against the database, so disabling, deleting or expiring a key takes effect on the next request to the Cloud API. At the gateway, a key stops at the moment it expires too, and disabling or deleting it takes up to 1 minute (see [Using a key at the gateway](#using-a-key-at-the-gateway)).

The raw key is never stored. It exists only at creation time. After you close the creation dialog in the dashboard, the only copy is the one you saved.

## Key format

A key is `tk_live_` or `tk_test_` followed by 43 letters, digits, hyphens and underscores. The prefix is the environment: `tk_live_` for Live and `tk_test_` for Test. It is part of the key, so send the whole key exactly as it was shown when you created it.

The **API Keys** page labels each key with its first 12 characters, for example `tk_live_AbCd`, so you can tell your keys apart without showing the key.

<Note>An older key is 64 hex characters and the page labels it with `tk_` and eight characters. It keeps working on the Cloud API, but the gateway does not accept it. To use one at the gateway, rotate it on the **API Keys** page and use the new key.</Note>

## Using a key at the gateway

The gateway takes the same key as `Authorization: Bearer`. The key must hold the `gateway:proxy` scope, and the person who made it must still have a role that can run scans (Owner, Admin, Security Lead or Member). The gateway exchanges the key for a short-lived token that carries your organization, your plan and the plan's limits, and applies them to every request:

| Gateway requests a minute | Free | Pro | Enterprise | Custom |
|---|---|---|---|---|
| Per organization | 100 | 1,000 | 5,000 | 20,000 |
| Per API key | 10 | 60 | 300 | 1,000 |

Requests over either limit get `429 Too Many Requests` with a `Retry-After` header. See [Gateway limits by plan](/api/rate-limits#gateway-limits-by-plan).

A key you revoke, disable or delete stops working at the gateway within 1 minute, because the gateway keeps the token it exchanged until the token expires. On the Cloud API the key is rejected at once. A key that reaches its expiry date stops at that moment on both: the token the gateway holds never outlives the key.

<Note>An organization with an IP allowlist cannot use API keys at the gateway yet. The gateway returns `401` for those keys. They keep working on the Cloud API, where the allowlist applies.</Note>

A key without `gateway:proxy`, such as a Read Only key, is refused at the gateway with `403` and the message `Insufficient permissions`. The message does not name the scope, so give the key `gateway:proxy` to use the gateway. A key whose creator no longer has a role that can run scans, such as a Viewer or Billing Admin, is refused the same way. Service account keys are not checked against a person's role.

## Key scopes

Each key has a set of scopes. A request to a route that needs a scope the key doesn't have returns `403`. Scopes use colon notation:

| Scope | Routes that check it |
|-------|----------------------|
| `scan:read` | `GET /violations`, `/repositories`, `/repositories/:repoName`, `/compliance`, `/issues`; `POST /brain/context`, `/brain/sentinel-context` |
| `scan:write` | `POST /scan-results/ingest`, `/audit/credits` |
| `issues:read` | `GET /issues` (either `issues:read` or `scan:read` is enough) |
| `issues:write` | `POST /incidents/:violationId/acknowledge`, `/incidents/:violationId/actions` |
| `policies:read` | `GET /rules`, `/rules/:ruleId`, `/brain/policies`, `/org/extension-policy` |
| `policies:write` | `POST /rules`, `PATCH` and `DELETE /rules/:ruleId`, `POST /rules/:ruleId/publish` |
| `audit:read` | `GET /audit-log` |
| `reports:read` | `GET /reports`, `/reports/:id`, `/reports/schedules` |
| `reports:write` | `POST /reports/generate`, schedule create, update and delete |
| `notifications:write` | `POST /notifications/digest` |
| `gateway:proxy` | The gateway: `gateway.takumo.io/v1/messages` and `/v1/chat/completions`. No Cloud API route checks it |

`GET /credits/check` is the only route that takes any valid key with no scope, because it returns your own organization's credit balance. Every other route checks a scope.

A refused request returns `403` and names the missing scope:

```json
{
  "error": "Forbidden: API key lacks required scope: policies:write",
  "required_scopes": ["policies:write"]
}
```

A key with an empty scope list passes every Cloud API scope check. Keys made by the device flow before 19 November 2026 and service account keys can have an empty list. Keys made on the **API Keys** page always have at least one scope. An empty list also keeps working at the gateway until 24 December 2026. After that date a key needs `gateway:proxy`, so create a scoped key before then. The **API Keys** page shows the date next to each such key.

The gateway checks one scope, `gateway:proxy`. The Cloud API scopes above do not affect what a key can do at the gateway, and `gateway:proxy` does not unlock any Cloud API route.

Assign the minimum scopes needed. See [API Keys](/dashboard/api-keys) for how to set them.

## Rate limit headers

Gateway responses (`gateway.takumo.io`) include rate limit headers. The Cloud API does not send the `X-RateLimit-*` headers; on a `429` it sends `Retry-After`.

| Header | Description |
|--------|-------------|
| `X-RateLimit-Limit` | Maximum requests allowed in the current window |
| `X-RateLimit-Remaining` | Requests remaining in the current window |
| `X-RateLimit-Reset` | Unix timestamp when the window resets |
| `Retry-After` | Seconds to wait before retrying (only present on `429` responses) |

Example response headers:

```
X-RateLimit-Limit: 60
X-RateLimit-Remaining: 42
X-RateLimit-Reset: 1710360000
```

When you receive a `429 Too Many Requests`, stop and wait for the number of seconds specified in `Retry-After`. See [Rate Limits](/api/rate-limits) for per-plan limits.

## Key rotation

For zero-downtime rotation:

1. Create a new key with the same scopes.
2. Deploy the new key to your tools.
3. Verify requests succeed with the new key.
4. Revoke the old key.

A revoked key returns `401 unauthorized` from the Cloud API at once and from the gateway within 1 minute. You can enable a disabled key again from the **API Keys** page while your organization is under its key limit. A deleted key cannot be restored.

## Error responses

| Status | Code | When |
|--------|------|------|
| `401` | `unauthorized` | Missing key, invalid key, expired key, revoked key |
| `403` | `forbidden` | Key lacks required scope, feature not available on your plan, request from outside the IP allowlist |
| `429` | `rate_limited` | Too many requests in the current window |

See [Errors](/api/errors) for the full error response format.
