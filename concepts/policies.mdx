# Policies

Policies define how Takumo checks your pull requests: which findings fail a check, which only warn, and which only comment. Block and Warn results are also recorded as violations.

<Note>
Policies apply to pull request checks on GitHub, GitLab and Bitbucket Server. The gateway, the editor extension and the CLI do not apply organization policies.
</Note>

## What a policy contains

Every policy has three parts:

| Part | What it controls |
|------|-----------------|
| **Rules** | The conditions that trigger the policy |
| **Enforcement mode** | What happens when a rule matches |
| **Scope** | Which repositories the policy covers |

## Enforcement modes

Four modes. Pick the one that matches your risk tolerance.

### Block

The pull request check fails and Takumo posts a comment with the details. Use this for findings that must not merge.

### Warn

The check passes and Takumo posts a comment with the details. On GitHub the check reports as neutral.

Use this for medium-severity findings where you want visibility without blocking work.

### Notify

The check passes and Takumo posts a comment with the details.

### Monitor

The check passes and Takumo posts a comment with the details.

Use this when rolling out a new policy. Watch what it matches before deciding whether to warn or block.

## Default detection patterns

Aegis Shield detects the most common secret types in outbound AI requests:

- AWS access keys and secret keys
- Database connection strings (PostgreSQL, MySQL, MongoDB, Redis)
- Stripe API keys and webhook secrets
- GitHub personal access tokens
- JWT tokens
- Private keys (RSA, EC, OpenSSH, PGP)
- Generic patterns (`password`, `secret`, `api_key` in variable names)

These are detected secrets, not a guarantee that every secret is found. Policies do not change what Aegis Shield detects.

## Custom policies

Create your own policies in the dashboard under **Policies** in the sidebar. The wizard offers policy templates and lets you set the rules, enforcement mode and scope.

Policy rules currently match on file names and on changes to dependency manifests. They do not read file contents. A secret rule, for example, matches files such as `.env` or `.pem`, not the secrets inside other files. Only some rule criteria are evaluated today, and the policy templates for OWASP Top 10, SOC 2 Baseline and PCI DSS do not trigger yet. See [Security Policies](/dashboard/rules) for the criteria and their current behavior.

## Custom Sentinel rules

In addition to policies, you can create **Sentinel rules** that scan inbound code for security issues.

Create them in the dashboard or directly from the extension:

```json
{
  "name": "no-eval",
  "pattern": { "type": "regex", "value": "eval\\(" },
  "severity": "critical",
  "category": "security",
  "message": "eval() is dangerous — use a safer alternative",
  "fixSuggestion": "Use JSON.parse() for data or Function() for dynamic code"
}
```

Rules sync automatically to all team members' daemons when published.

## Org extension policies

Organizations can enforce extension settings across all team members. This is useful for compliance:

| Setting | What it controls |
|---------|-----------------|
| **Forced settings** | Settings that members cannot override (e.g., force `scan.onSave: true`) |
| **Blocked settings** | Settings members cannot change at all |
| **Compliance mode** | Enforces a minimum set of security settings |
| **Minimum version** | Requires a specific extension version or newer |

Forced settings show a lock indicator in the extension's side panel. Members see the setting value but can't change it.

## Policy scope

Apply a policy to a set of repositories:

| Scope | What it covers |
|-------|---------------|
| **All repositories** | Every repository in the organization |
| **Repositories** | The repositories you name |
| **Tags** | Repositories that match the tags |

## Example: phased rollout

A common pattern for introducing a new policy:

1. Create the policy in **Monitor** mode
2. Watch matches for a week. Check for false positives.
3. Switch to **Warn** mode. Pull requests show a warning but are not blocked.
4. After another week with no complaints, switch to **Block** mode.

This takes about two weeks. You get data at every step. No surprises.
