Policies are the core enforcement mechanism in Takumo. Each policy groups one or more rules under a single configuration, with scoping, enforcement mode and version history. Policies apply to pull request checks and generate violations when a pull request does not comply.

The policies page is at **Dashboard → Policies**.

---

## Policy types

Every policy has a type that determines what kind of rules it can contain:

| Type | Description |
|------|-------------|
| **Security** | Detected secrets on the lines a pull request adds, and a lock file change flag. CVE thresholds, fix availability and scan freshness are not checked yet, and the wizard marks them **Not checked yet** |
| **License** | Not available yet. License lists are not checked against real licenses, so license rules never match. Existing license policies show **Not checked yet** |
| **Operational Risk** | Dependency health criteria (inactivity, contributor count, download volume, version lag, deprecation). These are not checked yet: the deprecated and version lag criteria match any lock file change, and the rest are saved only |

---

## Policy lifecycle

A policy moves through three statuses:

| Status | Meaning |
|--------|---------|
| **Draft** | Not enforced. Editable. Use this for testing before rollout. |
| **Active** | Enforced across matching repositories. Violations are tracked. |
| **Paused** | Temporarily disabled. Rules remain configured but do not trigger. |

Policies are soft-deleted. Deleting a policy removes it from the list and stops enforcement, but the record is preserved in the database.

---

## Enforcement modes

Each policy has an enforcement mode that controls what happens when a rule matches:

| Mode | Behavior |
|------|----------|
| **Block** | Blocks the PR merge or fails the check. |
| **Warn** | Surfaces a warning but allows the merge. |
| **Notify** | Does not affect the PR. Takumo posts a comment on the PR. |
| **Monitor** | Does not affect the PR. Takumo posts a comment on the PR. |

The enforcement mode is derived from the first rule in the policy.

## Creating a policy

<Steps>
  <Step title="Open the policies page">
    Navigate to **Dashboard → Policies** and click **Create Policy**.
  </Step>
  <Step title="Configure basics">
    Set the policy name, description, and type (Security, License, or Operational Risk).
  </Step>
  <Step title="Add rules">
    Add one or more rules to the policy. Each rule has a name, description, priority, criteria specific to the policy type, an enforcement action (block, warn, notify, monitor), and an enabled toggle.

    The wizard offers criteria for CVSS thresholds, specific CVEs, secret types, finding age, fix availability, malicious package detection, scan freshness, license lists, inactivity, contributor minimums, downloads, and version lag. Policy checks currently evaluate only some of these. Secret rules read the lines a pull request adds. Other rules match on dependency manifest and lock file changes. CVSS, CVE, age, fix availability, scan freshness, inactivity (`maxInactivityMonths`), contributor and download criteria are saved but not evaluated yet. The malicious package, deprecated and version lag criteria match any lock file change and do not look up the package. License lists are not checked against real licenses, so license rules never match. The wizard marks every criterion it does not check as **Not checked yet**. A secret rule flags detected secrets on added lines, not every secret in your code: some formats are not detected yet, such as unquoted values in a `.env` file. A file with a secret-sounding name but no secret in its changes passes.
  </Step>
  <Step title="Set the scope">
    Apply the policy to all repositories, specific repositories by name, or repositories matching tags. Repository names match whatever their case, and the wizard suggests your connected repositories.

    Path filters limit the files the policy reads. Enter patterns relative to the repository root, separated by commas or new lines:

    | Field | Behavior |
    |-------|----------|
    | **Include patterns** | When set, the policy reads only files that match one of them. Empty means every file. |
    | **Exclude patterns** | The policy never reads a file that matches one of them. Exclude wins over include. |

    Patterns use `*` for one path segment, `**` for any depth, `?`, `[abc]` and `{a,b}`. A trailing slash means the whole directory. Dotfiles match. For example, `src/**` includes everything under `src`, and `**/*.example` excludes every `.example` file.

    Takumo rejects a pattern that is empty, longer than 256 characters, starts with `/` or `!`, contains `..`, a backslash or a control character, has unbalanced `[ ] { } ( )`, or is not a valid glob. You can have up to 50 patterns per field. The wizard shows the problem under the field and blocks **Continue** until it is fixed, and Takumo checks the same rules when it saves. A policy whose filters match no file in a pull request still counts as evaluated.
  </Step>
  <Step title="Choose activation">
    Activate immediately or save as draft. A grace period can be set, but enforcement starts immediately today.
  </Step>
</Steps>

## Dashboard stats

The policies page shows four summary cards at the top:

| Stat | Description |
|------|-------------|
| **Total policies** | Count of all non-deleted policies |
| **Active** | Policies with `active` status |
| **Violations (30d)** | Total violations triggered across all policies in the last 30 days |
| **Block rate** | Percentage of active policies using `block` enforcement |

Clicking a stat card filters the policy list to the relevant subset.

---

## Filtering

The policy list supports filtering by:

- **Type**: Security, License, Ops Risk
- **Status**: Active, Paused, Draft
- **Enforcement**: Block, Warn, Notify, Monitor
- **Search**: Text search across policy name, description, and rule names

Active filters appear as removable chips below the filter bar.

---

## Policy actions

From the policy list, you can:

- **Expand** a policy card to see its rules, scope, version history, and metadata
- **Edit**: opens the policy in the create/edit sheet with all fields pre-populated
- **Toggle status**: switch between active, paused, and draft
- **Duplicate**: creates a copy of the policy in draft status
- **Delete**: soft-deletes the policy

---

## Version history

Every change to a policy creates a version record. The version history tracks:

- Version number
- Who made the change
- Change type (`created`, `rules_modified`, `scope_changed`, `status_changed`, `notifications_changed`, `grace_period_set`)
- Summary of what changed
- Field-level diffs (before/after values)

---

## Plan limits

The number of policies you can create depends on your plan. When you hit the limit, the **Create Policy** button is hidden and attempts to create via the API return an error with the limit and plan name.

Duplicating a policy also counts toward the limit.

| Action | Required scope |
|--------|---------------|
| View policies | `policies.read` |
| Create policies | `policies.create` |

## Alerts

A policy has no alert targets of its own. Violations alert the email addresses and Slack webhook in your organization's notification settings, and open tickets in connected trackers. Policies created before this change keep the targets they saved, but Takumo does not send to them.

## Sentinel AI review on policy checks

When Sentinel's AI review is on for your organization and it reports at least one failure finding, the check fails with **Takumo: Sentinel found N issues**, even when every policy passes. Suggestions alone never fail the check. A policy failure always comes first in the title.

A new review is skipped for a push within five minutes of the last review on the same pull request, and when the review rate limit, the daily cap or your credits run out. A skipped review does not fail the check, so treat the AI review as advice rather than a merge gate.
