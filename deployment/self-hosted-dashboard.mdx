The self-hosted dashboard is the Takumo web app (the `cloud` chart) running in your cluster on a hostname you own, with its own Postgres. Your users sign in there, and your GitHub App sends its webhooks there. Install it in the same namespace as the gateway and coordinator from [On-Premises](/deployment/onprem).

The dashboard image, `cr.takumo.io/takumo-cloud`, is private. Pulling it needs a [deploy token](/dashboard/deploy-tokens) from a Takumo workspace on the Pro or Enterprise plan that was created with the **On-Prem** deployment mode.

## Prerequisites

| Requirement | Notes |
|------------|-------|
| A Takumo workspace on Pro or Enterprise | Created with the **On-Prem** deployment mode. Its deploy token pulls the dashboard image. See [The image pull is denied](#the-image-pull-is-denied) |
| Kubernetes and Helm | The same cluster as [On-Premises](/deployment/onprem), with Helm 3.14 or later, or Helm 4. The upgrade commands on this page use `--reset-then-reuse-values`, which older Helm 3 releases do not have |
| PostgreSQL | A database for the dashboard. The coordinator reads tables the dashboard creates, so point `coordinator-database` at this same database |
| An Upstash compatible REST endpoint | Holds rate limits and single use tokens. See [Rate limiting backend](#rate-limiting-backend) |
| An email provider | [Resend](https://resend.com). The dashboard verifies each new account by email. See [Email](#email) |
| A hostname | For example `takumo.example.com`, pointed at your ingress controller |
| An ingress controller | The chart's Ingress uses class `nginx`. See [DNS and TLS](#dns-and-tls) |
| cert-manager and a ClusterIssuer | Issues the TLS certificate. You can bring your own certificate instead. See [DNS and TLS](#dns-and-tls) |

<Note>Support for a plain Redis endpoint, and for creating the first admin account without email, is planned. Until then, the REST endpoint and the email provider are both required.</Note>

### Outbound access

What the install must reach depends on the features you turn on. Allow only these:

| Destination | Needed for |
|------------|------------|
| Your registry, or `cr.takumo.io` with a [deploy token](/dashboard/deploy-tokens) | Pulling images. Each node's container runtime pulls, so allow this from every node, not only from pods |
| Your PostgreSQL and your Upstash compatible endpoint | Always |
| `github.com`, `api.github.com` | GitHub sign-in and your GitHub App |
| `oauth2.googleapis.com`, `www.googleapis.com` | Google sign-in. Users' browsers also reach `accounts.google.com` |
| `api.resend.com` | Email |
| `api.anthropic.com`, `api.openai.com` | The gateway, for the providers you configure |
| `rtb.takumo.io` | The license agent in a connected install only |

The install sends nothing else to Takumo. It does not need `charts.takumo.io` at runtime: only the machine that runs `helm` reaches it. When the dashboard starts, its database migration step may look up `registry.npmjs.org`. It does not need the answer, so blocking that host is fine.

Your GitHub App's webhooks travel the other way: `github.com` must reach `https://<your-dashboard-host>/api/integrations/github/webhook`. If the dashboard is not reachable from the internet, expose that path through a public ingress or a tunnel, or GitHub events never arrive.

### Air-gapped installs

With no route out, mirror every image into your own registry (see [Images](#images)) and use an [air-gapped license](#license). The dashboard verifies each new account by email, so allow `api.resend.com` for [email](#email). If you cannot, contact Takumo support at [support@takumo.io](mailto:support@takumo.io) before you install.

## Images

Each image on `cr.takumo.io` is a multi-architecture index for `linux/amd64` and `linux/arm64`. Pin a tag in every install. A chart left on `latest` can run different code on two installs a day apart.

<Steps>
  <Step title="Log in to cr.takumo.io">
    The username is your workspace ID and the password is a [deploy token](/dashboard/deploy-tokens). Paste the token when asked; it is read without echo:

    ```bash
    (
      printf 'Paste the deploy token, then press Enter: ' >&2
      read -rs TAKUMO_DEPLOY_TOKEN || exit 1
      echo >&2
      printf '%s' "$TAKUMO_DEPLOY_TOKEN" | crane auth login cr.takumo.io -u <workspace-id> --password-stdin
    )
    ```

    Log in to your own registry the same way.
  </Step>

  <Step title="Pick a tag">
    ```bash
    crane ls cr.takumo.io/aegis-shield
    ```
  </Step>

  <Step title="Copy each image by digest">
    `crane copy` copies the whole index, so both architectures arrive with the same digest:

    ```bash
    for image in aegis-shield gateway-coordinator sentinel-service vault-service takumo-rtb; do
      digest=$(crane digest "cr.takumo.io/$image:<tag>")
      crane copy "cr.takumo.io/$image@$digest" "<your-registry>/$image:<tag>"
    done
    crane copy cr.takumo.io/mirror/redis:7-alpine <your-registry>/mirror/redis:7-alpine
    ```

    The dashboard image has its own version, the chart's app version (`0.3.1` for chart `0.3.2`). Copy it the same way:

    ```bash
    digest=$(crane digest cr.takumo.io/takumo-cloud:0.3.1)
    crane copy "cr.takumo.io/takumo-cloud@$digest" <your-registry>/takumo-cloud:0.3.1
    ```

    Add `--insecure` to `crane copy` if your registry serves plain HTTP. Check that both platforms arrived:

    ```bash
    crane manifest <your-registry>/aegis-shield:<tag> | grep architecture
    ```
  </Step>

  <Step title="Point the charts at your registry">
    Set `image.repository` and `image.tag` on each chart, for example `--set image.repository=<your-registry>/aegis-shield --set image.tag=<tag>`, and put your registry's credentials in `takumo-pull-secret`. The dashboard chart uses `takumo-pull-secret` on its own only for images from `cr.takumo.io`, so for a mirrored dashboard image also set `--set imagePull.existingSecret=takumo-pull-secret`.
  </Step>
</Steps>

`<your-registry>` may carry a port, such as `registry.example.com:5000`, for every chart, including `takumo-rtb` from chart version 0.2.3. Every node must be able to pull from the registry, so configure each node's container runtime to trust its certificate, or to use plain HTTP, before you install.

## Install the dashboard

<Note>The blocks on this page use `read -rs` and `<(...)`, which need bash or zsh.</Note>

<Steps>
  <Step title="Create the image pull Secret">
    Skip this step if you created `takumo-pull-secret` in the `takumo` namespace for [On-Premises](/deployment/onprem). Otherwise, create the namespace if it does not exist yet:

    ```bash
    kubectl create namespace takumo
    ```

    Then issue a deploy token in the Takumo dashboard (**Settings > Deploy Tokens**) of the Pro or Enterprise workspace. The username is your workspace ID, which that page shows, and the password is the token. Replace `<workspace-id>` below, paste the whole block, then paste the token when asked. The token is read without echo, so it stays out of shell history, the screen and process arguments:

    ```bash
    (
      printf 'Paste the deploy token, then press Enter: ' >&2
      read -rs TAKUMO_DEPLOY_TOKEN || exit 1
      echo >&2
      printf '{"auths":{"cr.takumo.io":{"username":"%s","password":"%s"}}}' "<workspace-id>" "$TAKUMO_DEPLOY_TOKEN" \
        | kubectl create secret generic takumo-pull-secret -n takumo \
            --type=kubernetes.io/dockerconfigjson --from-file=.dockerconfigjson=/dev/stdin
    )
    ```

    `helm install` stops with the commands to fix it if this Secret is missing from the namespace or has the wrong type.
  </Step>

  <Step title="Download the chart">
    The on-prem values overlay, `values-onprem.yaml`, ships inside the chart. If you have not added the Helm repository yet, run `helm repo add takumo https://charts.takumo.io` first:

    ```bash
    helm repo update
    helm pull takumo/cloud --version 0.3.2 --untar --untardir ./takumo-charts
    ```
  </Step>

  <Step title="Create the database Secret">
    Paste the pooled and direct connection strings when asked, in the form `postgres://USER:PASSWORD@HOST:5432/DATABASE` (use the same URL twice if you have no pooler). The direct URL runs the migrations:

    ```bash
    (
      printf 'Pooled database URL: ' >&2; read -rs DB_URL || exit 1; echo >&2
      printf 'Direct database URL: ' >&2; read -rs DB_URL_DIRECT || exit 1; echo >&2
      kubectl create secret generic cloud-database -n takumo \
        --from-file=database-url=<(printf '%s' "$DB_URL") \
        --from-file=database-url-direct=<(printf '%s' "$DB_URL_DIRECT")
    )
    ```
  </Step>

  <Step title="Generate the auth and cron Secrets">
    Each value is 64 hex characters with no trailing newline. A newline breaks the value, so keep `tr -d '\n'`:

    ```bash
    kubectl create secret generic cloud-auth -n takumo \
      --from-file=better-auth-secret=<(openssl rand -hex 32 | tr -d '\n') \
      --from-file=encryption-key=<(openssl rand -hex 32 | tr -d '\n') \
      --from-file=hmac-key=<(openssl rand -hex 32 | tr -d '\n') \
      --from-file=sso-encryption-key=<(openssl rand -hex 32 | tr -d '\n')

    kubectl create secret generic cloud-cron -n takumo \
      --from-file=cron-secret=<(openssl rand -hex 32 | tr -d '\n')
    ```

    <Warning>`encryption-key` encrypts the integration credentials the dashboard stores. Back it up. A new key cannot read what the old one wrote.</Warning>
  </Step>

  <Step title="Create the rate limiting Secret">
    Paste the REST URL and token of your Upstash compatible endpoint:

    ```bash
    (
      printf 'REST URL: ' >&2; read -rs REDIS_URL || exit 1; echo >&2
      printf 'REST token: ' >&2; read -rs REDIS_TOKEN || exit 1; echo >&2
      kubectl create secret generic cloud-redis -n takumo \
        --from-file=upstash-redis-rest-url=<(printf '%s' "$REDIS_URL") \
        --from-file=upstash-redis-rest-token=<(printf '%s' "$REDIS_TOKEN")
    )
    ```
  </Step>

  <Step title="Create the email Secret">
    Paste your Resend API key when asked:

    ```bash
    (
      printf 'Paste your Resend API key, then press Enter: ' >&2
      read -rs RESEND_API_KEY || exit 1
      echo >&2
      printf '%s' "$RESEND_API_KEY" \
        | kubectl create secret generic cloud-email -n takumo --from-file=resend-api-key=/dev/stdin
    )
    ```
  </Step>

  <Step title="Install the content scanner">
    The dashboard's pull request check scans the files in a pull request for detected secrets through `sentinel-service`, so install it before the dashboard:

    ```bash
    helm pull takumo/sentinel-service --version 0.1.6 --untar --untardir ./takumo-charts
    helm install sentinel-service takumo/sentinel-service \
      --namespace takumo \
      --version 0.1.6 \
      --values ./takumo-charts/sentinel-service/values-onprem.yaml \
      --set secrets.imagePull.enabled=true \
      --set secrets.imagePull.secretName=takumo-pull-secret
    ```

    If you mirrored the image, add `--set image.repository=<your-registry>/sentinel-service --set image.tag=<tag>`. `values-onprem.yaml` admits the dashboard's pods on port 50051, and the dashboard chart sends its scan traffic there (`features.contentScan`). Wait for the pod before you continue:

    ```bash
    kubectl rollout status deploy/sentinel-service -n takumo
    ```

    Without it the dashboard still runs, but a pull request check cannot scan file contents. The check then says so in plain words and follows the organization's fail open or fail closed setting.
  </Step>

  <Step title="Install the chart">
    ```bash
    helm install cloud takumo/cloud \
      --namespace takumo \
      --version 0.3.2 \
      --values ./takumo-charts/cloud/values-onprem.yaml \
      --set app.url=https://<your-dashboard-host> \
      --set app.authUrl=https://<your-dashboard-host> \
      --set app.trustedOrigins=https://<your-dashboard-host> \
      --set app.cookieDomain=.<your-domain> \
      --set features.email=true \
      --set secrets.email.enabled=true \
      --set app.fromEmail='Takumo <takumo@<your-domain>>' \
      --set ingress.enabled=true \
      --set ingress.hostname=<your-dashboard-host> \
      --set ingress.tls.issuer=<your-cluster-issuer>
    ```

    The chart pulls `cr.takumo.io/takumo-cloud:0.3.1` with `takumo-pull-secret`. It refuses to install while `app.url`, `app.authUrl`, `app.cookieDomain` or `ingress.hostname` is empty, or while `app.fromEmail` is empty with `features.email=true`. If you mirrored the image, add `--set image.repository=<your-registry>/takumo-cloud --set imagePull.existingSecret=takumo-pull-secret`.

    `values-onprem.yaml` sets:
    - `app.installMode: onprem`, so every organization created on this dashboard is an on-prem organization
    - `worker.enabled: true`, the background worker that turns detected secrets and vulnerabilities into issues, syncs Bitbucket and resets annual credits. Without NATS it logs `running in HTTP push + cron only mode`, which is expected
    - `networkPolicy.enabled: true`, `replicaCount: 2` and billing, email and OAuth off, so the email flags above turn email on
    - `features.contentScan: true`, which lets the dashboard reach `sentinel-service` on port 50051 for the pull request check's file scan
    - `networkPolicyCheck.enabled: true`, which adds the two pods that `helm test` runs in the next step, and the ServiceAccount, Role and RoleBinding the second pod uses (they are ordinary resources, so every install and upgrade renders them; the Role can only get one named pod and its log)

    Watch the pods start. The first start runs the database migrations:

    ```bash
    kubectl get pods -n takumo -l app.kubernetes.io/name=cloud
    ```
  </Step>

  <Step title="Check that the content scanner is isolated">
    Run the check once `sentinel-service` and the dashboard are up:

    ```bash
    helm test cloud --namespace takumo --logs --timeout 10m
    ```

    It runs two short pods. The first has no dashboard label and tries to reach `sentinel-service` on port 50051. The second has the dashboard label, repeats the attempt and prints the verdict. Each line ends with the pod's start time in UTC. Read Helm's own error first, and trust a verdict only when its time is from this run: if a pod could not start or was killed, `--logs` can show a line from an earlier run.

    | The verdict says | What it means | What to do |
    |------------------|---------------|------------|
    | `enforced` | A pod without the dashboard label could not reach `sentinel-service` on port 50051, and the dashboard pod could. The check does not test any other pod, including the gateway | Nothing |
    | `WARNING: sentinel-service is reachable from any pod` | This cluster's network plugin does not enforce NetworkPolicy, or the `sentinel-service` policy is off. Any pod can call the scanner | See [Network policy](#network-policy) |
    | `inconclusive` | The check could not tell, for example because `sentinel-service` was still starting or the dashboard could not reach it | Check that `sentinel-service` is running, then run the command again |

    A failed check does not stop the install. The WARNING exits with success.
  </Step>

  <Step title="Open the dashboard">
    Go to `https://<your-dashboard-host>`, create your account, then create your organization.
  </Step>
</Steps>

### DNS and TLS

Point `<your-dashboard-host>` at your ingress controller. The chart's Ingress uses class `nginx` (`ingress.className`) and the TLS Secret `cloud-tls` (`ingress.tls.secretName`). With `ingress.tls.issuer` set, cert-manager issues the certificate through that ClusterIssuer. To use your own certificate, set `--set ingress.tls.issuer=""` and create the Secret yourself:

```bash
kubectl create secret tls cloud-tls -n takumo --cert=./tls.crt --key=./tls.key
```

<Warning>The dashboard's NetworkPolicy admits traffic only from the namespace named `ingress-nginx`. If your ingress controller runs in another namespace and your CNI enforces NetworkPolicy, requests time out. Run the controller in `ingress-nginx`, or install with `--set networkPolicy.enabled=false` and apply your own policy.</Warning>

### Rate limiting backend

The dashboard keeps rate limits and single use tokens through the Upstash REST API, not the Redis protocol. Use an [Upstash](https://upstash.com) database, or run an Upstash compatible REST proxy such as [serverless-redis-http](https://github.com/hiett/serverless-redis-http) in front of your own Redis. The dashboard's NetworkPolicy allows egress on port 443 and 5432 only (and on port 50051 to `sentinel-service` when `features.contentScan` is on), so serve the endpoint on 443.

Without the endpoint the pods never become ready: `/api/health/ready` answers 503 and the dashboard's log names `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN`. If the endpoint is unreachable, each rate limited request waits about 5 seconds and is then allowed, and connecting GitHub fails with **GitHub could not be connected right now**.

### Email

The dashboard sends email through Resend, set up in [Install the dashboard](#install-the-dashboard). Without it, nothing is sent: sign-up says a verification link was sent, but an account created with email and password stays unverified and cannot sign in, and password reset emails never arrive.

Use a sender on a domain you have verified in Resend.

### Monitoring

The dashboard sends traces and metrics over OpenTelemetry (OTLP over HTTP). Point it at your collector with `otel.endpoint`. An https endpoint works anywhere; plain http works only for a service inside the cluster, such as `http://otel-collector.monitoring.svc.cluster.local:4318`. Over plain http the dashboard sends no credentials to the collector. The dashboard's NetworkPolicy allows outbound traffic on ports 443 and 5432 only (and on port 50051 to `sentinel-service` when `features.contentScan` is on), so add a rule for the collector:

```bash
helm upgrade cloud takumo/cloud --version 0.3.2 --reset-then-reuse-values \
  --set otel.endpoint=http://otel-collector.monitoring.svc.cluster.local:4318 \
  --set-json 'networkPolicy.extraEgress=[{"to":[{"namespaceSelector":{"matchLabels":{"kubernetes.io/metadata.name":"monitoring"}}}],"ports":[{"port":4318,"protocol":"TCP"}]}]'
```

`takumo_config_valid` is 1 when the dashboard's configuration passed its startup check and 0 when it did not; `takumo_config_problems` names each variable that failed. With the Prometheus Operator installed, `--set alerting.enabled=true` adds alert rules, including one that fires when the configuration is invalid.

### Live notifications

Notifications arrive in the dashboard within 30 seconds. To deliver them instantly, give the dashboard a Redis server for pub/sub with `--set features.redisPubSub=true --set features.redisPubSubUrl=redis://<redis-host>:6379`, and allow port 6379 to it with a `networkPolicy.extraEgress` rule like the one in [Monitoring](#monitoring).

### Upgrading from 0.3.0

Upgrade every Cloud release with `--reset-then-reuse-values`, not `--reuse-values`: `--reuse-values` keeps the old release's values and drops settings the new chart adds. Chart 0.3.1 added `features.contentScan` and `networkPolicyCheck.enabled`, so set both on the first upgrade, after you install `sentinel-service` as in [Install the dashboard](#install-the-dashboard):

```bash
helm upgrade cloud takumo/cloud \
  --namespace takumo \
  --version 0.3.2 \
  --reset-then-reuse-values \
  --set features.contentScan=true \
  --set networkPolicyCheck.enabled=true
```

Do not pass `--values values-onprem.yaml` to an upgrade. That file carries empty `app.url`, `app.authUrl`, `app.cookieDomain` and `app.trustedOrigins`, so it would replace your install's own values, and the chart refuses to render. Then run `helm test cloud --namespace takumo --logs --timeout 10m`.

## Sign in with GitHub or Google

Sign-in uses an OAuth app per provider. Set the callback URL exactly:

| Provider | Where | Callback URL |
|----------|-------|--------------|
| GitHub | **Settings > Developer settings > OAuth Apps > New OAuth App** | `https://<your-dashboard-host>/api/auth/callback/github` |
| Google | Google Cloud console, **APIs & Services > Credentials > Create credentials > OAuth client ID**, type **Web application** | `https://<your-dashboard-host>/api/auth/callback/google` |

For GitHub, set the homepage URL to `https://<your-dashboard-host>`. While the Google consent screen's publishing status is **Testing**, only the test users you list can sign in. Move it to **In production** before you open sign-in to everyone.

A user who signs in with GitHub or Google takes the address the provider has verified, so they can sign in without email.

The Secret needs all four keys. Leave the pair for a provider you do not use empty:

```bash
(
  printf 'GitHub client ID: ' >&2; read -rs GH_ID || exit 1; echo >&2
  printf 'GitHub client secret: ' >&2; read -rs GH_SECRET || exit 1; echo >&2
  printf 'Google client ID: ' >&2; read -rs GOOGLE_ID || exit 1; echo >&2
  printf 'Google client secret: ' >&2; read -rs GOOGLE_SECRET || exit 1; echo >&2
  kubectl create secret generic cloud-oauth -n takumo \
    --from-file=github-client-id=<(printf '%s' "$GH_ID") \
    --from-file=github-client-secret=<(printf '%s' "$GH_SECRET") \
    --from-file=google-client-id=<(printf '%s' "$GOOGLE_ID") \
    --from-file=google-client-secret=<(printf '%s' "$GOOGLE_SECRET")
)
```

```bash
helm upgrade cloud takumo/cloud \
  --namespace takumo \
  --version 0.3.2 \
  --reset-then-reuse-values \
  --set features.oauth=true \
  --set secrets.oauth.enabled=true
```

## Your GitHub App

A self-hosted dashboard connects repositories through a GitHub App you own. Create it under the GitHub organization that owns your repositories: **Settings > Developer settings > GitHub Apps > New GitHub App**.

| Field | Value |
|-------|-------|
| GitHub App name | Any name, for example `Acme Takumo`. GitHub derives the app's slug from it |
| Homepage URL | `https://<your-dashboard-host>` |
| Callback URL | `https://<your-dashboard-host>/api/integrations/github/authorize/callback` |
| Request user authorization (OAuth) during installation | Unchecked |
| Setup URL | `https://<your-dashboard-host>/api/integrations/github/callback`, with **Redirect on update** checked |
| Webhook URL | `https://<your-dashboard-host>/api/integrations/github/webhook`, with **Active** checked |
| Webhook secret | The value from `webhook-secret.txt` below |
| Where can this GitHub App be installed? | **Only on this account** |

Generate the webhook secret without a trailing newline, and paste the file's contents into the form:

```bash
openssl rand -hex 32 | tr -d '\n' > webhook-secret.txt
```

**Repository permissions:**

| Permission | Access |
|-----------|--------|
| Actions | Read-only |
| Administration | Read-only |
| Checks | Read and write |
| Code scanning alerts | Read-only |
| Contents | Read and write |
| Dependabot alerts | Read-only |
| Issues | Read and write |
| Metadata | Read-only |
| Pull requests | Read and write |
| Secret scanning alerts | Read-only |
| Workflows | Read and write |

**Organization permissions:**

| Permission | Access |
|-----------|--------|
| Members | Read-only |

Before it binds an installation, the dashboard asks GitHub to prove that the person connecting controls it: after the install, GitHub asks them to authorize the app, and the dashboard checks that they own the account or are an owner of the organization. That is why the app needs a callback URL, the Members permission and a client secret. Leave **Request user authorization (OAuth) during installation** unchecked: with it checked, GitHub sends the installer to the callback URL instead of the setup URL, and the connection never completes.

**Subscribe to events:** Branch protection rule, Check suite, Code scanning alert, Dependabot alert, Issues, Pull request, Push, Secret scanning alert and Workflow run. GitHub sends installation events to every app without a subscription.

After you create the app, note its **App ID**, its **Client ID** and its slug (the last part of `https://github.com/apps/<slug>`). Then generate a private key and a client secret on the app's **General** page. GitHub downloads the private key as a `.pem` file, which the Secret accepts as is, or its base64 encoding. GitHub shows the client secret once: save it to a file without a trailing newline.

```bash
printf 'GitHub App client secret: ' >&2; read -rs GH_APP_SECRET; echo >&2
printf '%s' "$GH_APP_SECRET" > client-secret.txt; unset GH_APP_SECRET
kubectl create secret generic cloud-github-app -n takumo \
  --from-file=github-app-private-key=./<your-app>.private-key.pem \
  --from-file=github-webhook-secret=./webhook-secret.txt \
  --from-file=github-app-client-secret=./client-secret.txt
rm webhook-secret.txt client-secret.txt
```

Pass the App ID with `--set-string`, so Helm keeps it as a string. The client ID tells the dashboard to read `github-app-client-secret` from the same Secret:

```bash
helm upgrade cloud takumo/cloud \
  --namespace takumo \
  --version 0.3.2 \
  --reset-then-reuse-values \
  --set features.githubApp=true \
  --set secrets.githubApp.enabled=true \
  --set-string app.githubAppId=<app-id> \
  --set app.githubAppSlug=<slug> \
  --set app.githubAppClientId=<client-id>
```

Then connect GitHub from **Integrations** in your dashboard. An owner of the GitHub organization, or the owner of a personal account, installs the app and authorizes it when GitHub asks.

If your app was already connected before you added the client secret, add it to the existing `cloud-github-app` Secret instead of recreating the Secret, then run the `helm upgrade` above:

```bash
printf 'GitHub App client secret: ' >&2; read -rs GH_APP_SECRET; echo >&2
kubectl -n takumo patch secret cloud-github-app --type merge --patch-file /dev/stdin \
  <<<"{\"data\":{\"github-app-client-secret\":\"$(printf '%s' "$GH_APP_SECRET" | base64)\"}}"
unset GH_APP_SECRET
```

<Note>If connecting GitHub says **Connecting GitHub is not configured on this Takumo install**, the dashboard is missing the App or its client ID or client secret. The `config.invalid` log line names the setting. Existing connections keep working.</Note>

## License

Each install runs the `takumo-rtb` license agent. In an air-gapped install, the license is a signed file you download from the Takumo dashboard and store in a Secret.

<Steps>
  <Step title="Install the agent">
    ```bash
    helm install takumo-rtb takumo/takumo-rtb \
      --namespace takumo \
      --version 0.3.0 \
      --set rtb.airGapped=true \
      --set image.repository=<your-registry>/takumo-rtb \
      --set image.tag=<tag> \
      --set 'imagePullSecrets[0].name=takumo-pull-secret'
    ```
  </Step>

  <Step title="Read the install's fingerprint">
    ```bash
    kubectl -n takumo exec deploy/takumo-rtb -- takumo-rtb fingerprint
    ```
  </Step>

  <Step title="Add the install in the Takumo dashboard">
    In your workspace on the Takumo dashboard, open **Installations**, choose **Add air-gapped install**, enter the fingerprint, and choose **Add and download license** to get the license file, `license-<install-id>.json`.
  </Step>

  <Step title="Store the license">
    ```bash
    kubectl -n takumo create secret generic takumo-license --from-file=license=./license-<install-id>.json
    ```
  </Step>
</Steps>

A license is valid for 60 days. From day 46, use **Download refreshed license** on the same install's page and replace the Secret:

```bash
kubectl -n takumo create secret generic takumo-license --from-file=license=./license-<install-id>.json \
  --dry-run=client -o yaml | kubectl apply -f -
```

The agent's logs show its status: `kubectl -n takumo logs deploy/takumo-rtb`.

To see the stage every service reports, run `kubectl -n takumo exec deploy/takumo-rtb -- takumo-rtb check -n takumo`. For the stages and recovery steps, see [On-Prem Licensing](/deployment/onprem-licensing).

## Troubleshooting

For the misconfigured install page, the `config.invalid` log line, the GitHub App private key and failing cron jobs, see [Troubleshooting the self-hosted dashboard](/deployment/onprem#troubleshooting-the-self-hosted-dashboard).

### Pods hang or time out on an enforcing CNI

Takumo's charts create NetworkPolicies. CNIs such as Calico and Cilium enforce them; flannel does not, so a policy gap shows only on an enforcing CNI. If a pod hangs while connecting or a cron Job ends in `DeadlineExceeded`, check the namespace's policies and the connection the pod needs:

```bash
kubectl get networkpolicy -n takumo
kubectl describe networkpolicy -n takumo <policy-name>
```

The dashboard admits traffic from the `ingress-nginx` namespace, from pods labelled `app.kubernetes.io/part-of: takumo` and from its own cron jobs, and sends traffic out on 53, 443 and 5432, to the coordinator, and to `sentinel-service` on 50051 when `features.contentScan` is on, plus the license agent when `rtb.enabled` is on. The gateway's own limits are on [On-Premises](/deployment/onprem#network-requirements).

### Network policy

The `sentinel-service` NetworkPolicy admits the dashboard's pods and the gateway on port 50051 and refuses other pods. That isolation holds only on a CNI that enforces NetworkPolicy, such as Calico or Cilium. Flannel does not enforce it: on a flannel cluster every pod in the namespace can call `sentinel-service`, and the check in the install steps prints a WARNING that says so. The scanner returns findings only for content the caller sends and reads no stored data, but to isolate it, use a CNI that enforces NetworkPolicy and keep the `sentinel-service` policy on.

On a Linkerd-meshed install you can also restrict the gRPC port to named ServiceAccounts with `linkerdAuthz`; `values-onprem.yaml` in the `sentinel-service` chart shows the block, and `cloud-sa` is the dashboard's ServiceAccount. The check tests NetworkPolicy only. With `linkerdAuthz` on, the mesh proxy accepts the connection, so the check prints the WARNING even though authorization refuses the call.

### The image pull is denied

If the dashboard pods stay in `ImagePullBackOff`, read the pull error:

```bash
kubectl describe pods -n takumo -l app.kubernetes.io/name=cloud --show-events=true | grep -iA3 'failed to pull'
```

An error that says `denied`, `403 Forbidden`, or `This workspace is not entitled to the self-hosted dashboard image`, means the deploy token in `takumo-pull-secret` works but its workspace cannot pull the dashboard image. The workspace must be on the Pro or Enterprise plan and must have been created with the **On-Prem** deployment mode. Some container runtimes show only `denied`, or containerd only `403 Forbidden`, without the message. Issue a token from a workspace that meets both conditions, delete the old Secret with `kubectl delete secret takumo-pull-secret -n takumo`, and create it again as in [Install the dashboard](#install-the-dashboard).

An error that says `unauthorized` means the workspace ID or the token is wrong, or the token was revoked or has expired. See [Deploy Tokens](/dashboard/deploy-tokens).

An error that says `i/o timeout` means the node cannot reach `cr.takumo.io`. Each node's container runtime pulls the image, not the pod, so allow outbound 443 from every node (see [Outbound access](#outbound-access)), or mirror the image into your own registry (see [Images](#images)).

### GitHub does not connect

The error on the **Integrations** page names the step that failed. Then read the dashboard's logs around the time you clicked:

```bash
kubectl logs -n takumo deploy/cloud --since=10m | grep -iE 'github|config.invalid'
```

| What you see | Check |
|--------------|-------|
| GitHub shows a 404 instead of the install page | `app.githubAppSlug` matches the app's slug |
| **this install is misconfigured** | The `config.invalid` line names the setting: the App ID, slug, private key or webhook secret |
| **not configured on this Takumo install** | The `config.invalid` line names `GITHUB_APP_CLIENT_ID` or `GITHUB_APP_CLIENT_SECRET`: set `app.githubAppClientId` and the Secret's `github-app-client-secret` key |
| GitHub says **This GitHub App must be configured with a callback URL** | The app's **Callback URL** is empty. On the app's **General** page, add `https://<your-dashboard-host>/api/integrations/github/authorize/callback` and click **Save changes** at the bottom of the page |
| **Ask a GitHub organization owner to connect Takumo** | Only an owner of the GitHub organization can connect it. GitHub must have asked them to authorize the app: check that the app's callback URL is set |
| **GitHub could not be connected right now** | The [rate limiting backend](#rate-limiting-backend) is reachable |
| **belongs to a different GitHub App** | You installed another app. Install the one whose slug you configured |
| Repositories connect but no checks run | GitHub reaches your webhook URL: the app's **Advanced** tab lists each delivery and its response |
