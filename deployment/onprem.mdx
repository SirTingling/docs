For organizations that need full control over where their data flows. Deploy the gateway and coordinator in your Kubernetes cluster.

## Prerequisites

| Requirement | Minimum Version |
|------------|----------------|
| Kubernetes | 1.27+ |
| Helm | 3.x |
| PostgreSQL | 15+ (or Neon Postgres) |
| Redis | None to provide: the gateway chart runs its own Redis 7 (`redis.enabled: true`) |
| Container registry access | Outbound HTTPS to `cr.takumo.io` (Takumo's authenticated container registry, per-tenant deploy token) |

## Deployment

<Steps>
  <Step title="Add the Helm repository">
    ```bash
    helm repo add takumo https://charts.takumo.io
    helm repo update
    ```
  </Step>

  <Step title="Create namespace and secrets">
    ```bash
    kubectl create namespace takumo
    ```

    Create the database credentials for the coordinator. `database-url` is the
    pooled connection string and `database-url-direct` the direct one (use the
    same URL twice if you have no pooler). Paste each when asked, in the form
    `postgres://USER:PASSWORD@HOST:5432/takumo`. They are read without echo, so
    the password stays out of shell history:

    ```bash
    (
      printf 'Pooled database URL: ' >&2; read -rs DB_URL || exit 1; echo >&2
      printf 'Direct database URL: ' >&2; read -rs DB_URL_DIRECT || exit 1; echo >&2
      kubectl create secret generic coordinator-database -n takumo \
        --from-file=database-url=<(printf '%s' "$DB_URL") \
        --from-file=database-url-direct=<(printf '%s' "$DB_URL_DIRECT")
    )
    ```

    Generate the coordinator's JWT key pair. The coordinator signs ES256 tokens, so it needs a P-256 key, and the private key must be PKCS#8 (`BEGIN PRIVATE KEY`):

    ```bash
    openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out signing.pem
    openssl pkey -in signing.pem -pubout -out verification.pem
    ```

    Create the JWT signing and verification keys for the coordinator:

    ```bash
    kubectl create secret generic coordinator-jwt-signing \
      --namespace takumo \
      --from-file=signing.pem=./signing.pem \
      --from-file=verification.pem=./verification.pem
    ```

    Create the JWT public key for the gateway (this is the same `verification.pem` file, stored under the key `public.pem`):

    ```bash
    kubectl create secret generic aegis-jwt-key \
      --namespace takumo \
      --from-file=public.pem=./verification.pem
    ```

    Create the image pull Secret for `cr.takumo.io`. Issue a deploy token
    in the Takumo dashboard (**Settings > Deploy Tokens**). The username is
    your workspace ID, which that page shows, and the password is the token.
    Replace `<workspace-id>` below, paste the whole block, then paste the
    token when asked. The token is read without echo, so it stays out of
    shell history, the screen and process arguments. Full reference:
    [Deploy Tokens](/dashboard/deploy-tokens).

    ```bash
    (
      printf 'Paste the deploy token, then press Enter: ' >&2
      read -rs TAKUMO_DEPLOY_TOKEN || exit 1
      echo >&2
      printf '{"auths":{"cr.takumo.io":{"username":"%s","password":"%s"}}}' "<workspace-id>" "$TAKUMO_DEPLOY_TOKEN" \
        | kubectl create secret generic takumo-pull-secret -n takumo \
            --type=kubernetes.io/dockerconfigjson --from-file=.dockerconfigjson=/dev/stdin
    )
    ```

    **Air-gapped:** if your cluster has no egress to `cr.takumo.io`, mirror
    the four service images (`aegis-shield`, `gateway-coordinator`,
    `sentinel-service`, `vault-service`) plus `mirror/redis` into your
    internal registry. Override `image.repository` in your values file, and
    `redis.image.repository` for the gateway's Redis, then put that
    registry's pull credentials in this Secret instead.
  </Step>

  <Step title="Download the charts">
    The on-prem values overlay, `values-onprem.yaml`, ships inside each
    chart. Pull both charts and unpack them into a local folder:

    ```bash
    helm pull takumo/gateway-coordinator --version 0.1.2 --untar --untardir ./takumo-charts
    helm pull takumo/aegis-shield --version 0.2.2 --untar --untardir ./takumo-charts
    ```

    `helm show values` prints only the base `values.yaml`, not the overlay,
    so use the files from `./takumo-charts`. To find newer chart versions,
    run `helm search repo takumo --versions` and use the same version in
    every command on this page.
  </Step>

  <Step title="Deploy the coordinator">
    The coordinator uses the `manual` secrets provider for on-prem, meaning it expects you to create Kubernetes secrets yourself (done in the previous step).

    Deploy initially with the join key disabled (you'll create it in a later step):

    ```bash
    helm install gateway-coordinator takumo/gateway-coordinator \
      --namespace takumo \
      --version 0.1.2 \
      --values ./takumo-charts/gateway-coordinator/values-onprem.yaml \
      --set secrets.joinKey.enabled=false \
      --set secrets.imagePull.enabled=true \
      --set secrets.imagePull.secretName=takumo-pull-secret
    ```

    The overlay sets:
    - `secrets.provider: manual`
    - `secrets.database.enabled: true` with secret name `coordinator-database`
    - `secrets.jwtSigning.enabled: true` with secret name `coordinator-jwt-signing`

    The overlay turns the image pull Secret off, so the two `secrets.imagePull`
    flags point the pods at `takumo-pull-secret`. Without them the pods cannot
    pull from `cr.takumo.io`.

    <Note>The base chart defaults to `cloud-database` for the database secret name. The on-prem values overlay changes this to `coordinator-database` to match the secret created above.</Note>

    Verify the coordinator is running:

    ```bash
    kubectl get pods -n takumo -l app.kubernetes.io/name=gateway-coordinator
    ```
  </Step>

  <Step title="Deploy the gateway">
    Deploy with the join key disabled here too, since its Secret does not exist yet:

    ```bash
    helm install aegis-shield takumo/aegis-shield \
      --namespace takumo \
      --version 0.2.2 \
      --values ./takumo-charts/aegis-shield/values-onprem.yaml \
      --set connector.grpcUrl="gateway-coordinator.takumo.svc.cluster.local:9090" \
      --set secrets.joinKey.enabled=false \
      --set secrets.imagePull.enabled=true \
      --set secrets.imagePull.secretName=takumo-pull-secret
    ```

    This configures the gateway to connect to the coordinator over gRPC on port 9090 and disables the cloud connector (`cloud.enabled: false`).

    Verify the gateway is running:

    ```bash
    kubectl get pods -n takumo -l app.kubernetes.io/name=aegis-shield
    ```
  </Step>

  <Step title="Create a join key in the dashboard">
    Go to **Settings > Gateway** in the dashboard and click **Create join key**. Give it a name (for example `production-cluster`). Copy the key immediately.
  </Step>

  <Step title="Configure the gateway and coordinator with the join key">
    Create the join key Secrets for both the gateway and the coordinator. Paste
    the join key when asked; it is read without echo:

    ```bash
    (
      printf 'Paste the join key, then press Enter: ' >&2
      read -rs TAKUMO_JOIN_KEY || exit 1
      echo >&2
      for name in aegis-join-key coordinator-join-key; do
        printf '%s' "$TAKUMO_JOIN_KEY" \
          | kubectl create secret generic "$name" -n takumo --from-file=join-key=/dev/stdin
      done
    )
    ```

    Upgrade the gateway to use it:

    ```bash
    helm upgrade aegis-shield takumo/aegis-shield \
      --namespace takumo \
      --version 0.2.2 \
      --reuse-values \
      --set secrets.joinKey.enabled=true \
      --set secrets.joinKey.secretName=aegis-join-key
    ```

    Upgrade the coordinator to use it:

    ```bash
    helm upgrade gateway-coordinator takumo/gateway-coordinator \
      --namespace takumo \
      --version 0.1.2 \
      --reuse-values \
      --set secrets.joinKey.enabled=true
    ```
  </Step>

  <Step title="Verify the connection">
    Check the **Fleet** page in the dashboard. Your gateway instance should appear with a **Connected** state.

    You can also verify locally:

    ```bash
    kubectl logs -n takumo -l app.kubernetes.io/name=aegis-shield --tail=20
    ```

    Look for a log line indicating successful registration with the coordinator.
  </Step>
</Steps>

<Warning>The join key is shown once. Store it in your secrets management system (Vault, AWS Secrets Manager, etc.) before closing the dialog.</Warning>

## Required secrets reference

### Coordinator

| Secret Name | Keys | Description |
|------------|------|-------------|
| `coordinator-database` | `database-url`, `database-url-direct` | PostgreSQL connection strings (pooled and direct) |
| `coordinator-jwt-signing` | `signing.pem`, `verification.pem` | JWT signing and verification key pair |
| `coordinator-join-key` | `join-key` | Join key for gateway authentication (optional) |

### Gateway

| Secret Name | Keys | Description |
|------------|------|-------------|
| `aegis-jwt-key` | `public.pem` | JWT public key for auth verification |
| `aegis-join-key` | `join-key` | Join key for coordinator registration |
| `takumo-pull-secret` | Docker registry credentials | Image pull secret for `cr.takumo.io` (per-tenant deploy token from Takumo dashboard) |

## Network requirements

The gateway needs outbound access to:

- Your AI provider (for example `api.anthropic.com`, `api.openai.com`)
- The coordinator gRPC endpoint (port 9090)
- Its own Redis (port 6379)

The coordinator needs:

- Access to PostgreSQL
- Inbound gRPC from gateway pods (port 9090)
- Inbound HTTP for health checks (port 8080)

Both services create NetworkPolicy resources by default (`networkPolicy.enabled: true`).

<Warning>The gateway's NetworkPolicy in chart 0.2.2 allows egress only on ports 53 and 443. If your CNI enforces NetworkPolicy, it blocks the gateway's connections to the coordinator on 9090 and to its Redis on 6379. Add a NetworkPolicy that allows that egress from the gateway pods, or install the gateway with `--set networkPolicy.enabled=false` and apply your own.</Warning>
